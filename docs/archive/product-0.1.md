# 摄像头交互学习工具：产品与技术规格 v0.1

日期：2026-11-04。状态：供开发使用的初版规格，尚未实现或进行性能验证。

## 1. 已确认的产品目标

面向创意交互制作的中文工具。用户创建项目，选择摄像头检测方式，录制示例，建立动作匹配，再将动作绑定到可见的效果。

核心案例：录制约三秒的手指动作。在画面不同位置重复该动作，只要相对变化过程足够接近，就执行一次 A。需要识别完整时间过程，不能只识别最终姿态，也不能依赖几个固定像素区域。

- 当前输入方向：手部、面部、身体姿态。
- 不使用 OSC，不提供端口、OSC 地址、输入维数等配置。
- 中文界面，有明确的用途说明与状态反馈。
- 先做可交互的浏览器 demo，再复用核心代码制作 Mac application。
- 未来考虑物体检测框、标签和 GPT 视觉理解；首版不接入付费云端服务。

## 2. 推荐路线与取舍

采用 TypeScript + React + Vite 作为界面与浏览器 demo，MediaPipe Tasks Vision 进行本机检测，独立 TypeScript 核心处理特征、时序匹配与触发。后续优先评估 Electron 封装 Mac app。

这是基于当前目标的工程建议，不代表已完成兼容性或速度测试。

| 方案 | 适用情况 | 本项目建议 |
| --- | --- | --- |
| Web / TypeScript | 快速验证摄像头、中文界面、录制与实时反馈 | 首版主线；推理在用户设备执行 |
| Electron | 复用 Web 界面，提供桌面窗口和文件能力；内置 Chromium 与 Node.js | Mac 封装优先候选；代价是安装包和内存占用 |
| Tauri | 希望安装包更小，可接受 Rust 与系统 WebView 的集成 | 备选；macOS 使用 WKWebView，需另测摄像头、模型与 Worker |
| Python | 算法试验、离线数据分析或特定原生视觉库 | 按需用于研究，不作为首版用户安装依赖 |
| Java | 有现成 Java 团队、代码或框架时 | 当前没有必须选择它的理由；Wekinator 的实现语言不决定本项目语言 |

浏览器版须使用 localhost 或 HTTPS 获取摄像头权限。网页不会自动变成 Mac app；封装阶段还要完成权限配置、资源打包、桌面实测，正式分发另需处理签名与公证。

## 3. 分清三种选择

### 3.1 检测方式：摄像头看什么

| 中文名称 | 技术候选 | 用户可理解的说明 | 典型用途 |
| --- | --- | --- | --- |
| 手部追踪 | MediaPipe Hand Landmarker | 追踪手指关节与手的运动 | 捏合、展开手指、画圈、手势序列 |
| 面部追踪 | MediaPipe Face Landmarker | 追踪面部关键点与表情变化 | 张嘴、眨眼、表情变化；点头需另提取头部姿态 |
| 身体追踪 | MediaPipe Pose Landmarker | 追踪肩、肘、髋、膝等身体关节 | 抬手、转身、身体动作序列 |

用户提到的 PoseNet 在这里表达身体骨骼检测需求；首版建议用 Pose Landmarker，不需要为了名称强行绑定 PoseNet。

这些是预训练检测模型，通过本地 SDK/API 调用；“使用 API”并不必然意味着把视频发给服务器。检测器输出关键点，用户录制的示范由下一层学习，不重新训练骨骼检测网络。

首版提供三种可用的单一检测模式；每个项目一次启用一种，先支持一个人、单只手。双手、多人以及手脸身体同时融合后续扩展，不承诺首版同时运行三个模型。

### 3.2 学习方式：怎样解释检测数据

| 中文名称 | 界面说明 | 示例 | 阶段 |
| --- | --- | --- | --- |
| 动态动作匹配 | 识别一段完整动作，允许一定速度差异，完成后触发一次效果 | 三秒的手指变化 → 切换画面 | 首版核心 |
| 姿态分类 | 判断当前姿态最接近哪一类 | 握拳是 A，张掌是 B | 后续，标注“规划中” |
| 连续控制 | 将当前特征映射到持续变化的数值 | 捏合距离 → 图形大小 | 后续，标注“规划中” |

不能把未实现的学习方式表现为已可用。动态动作匹配采用模板方法时，“训练”实际执行特征处理、模板构建和阈值校准，不宣称训练了神经网络。

### 3.3 执行效果：识别成功后做什么

首版至少实现：切换应用内场景、播放内置动画。可加播放本地声音，但遵循浏览器用户启动播放的要求。每个动作绑定具体效果，可手动测试，运行时有最近触发记录。

不加入任意脚本执行或系统控制。未来外部软件联动的方式另定；目前不假定需要任何网络输出协议。

## 4. 中文界面与用户流程

### A. 项目首页

首页标题“项目”，直接提供“新建项目”“打开项目”与最近项目。最近项目展示名称和检测方式。无本地项目时显示“暂无本地项目”。不设置宣传主视觉、口号或品牌式页脚。保存能力真实可用后才显示保存成功。

### B. 新建项目

1. 填写项目名称。
2. 从手部、面部、身体卡片选择检测方式，每张卡片含说明与动作例子。
3. 选择学习方式；默认动态动作匹配，其余标记规划中。
4. 开启摄像头，显示预览、检测状态与取景提示，然后进入工作台。

首次页面不出现模型文件路径、特征维度或复杂算法参数。技术信息放“高级设置”。

### C. 学习工作台

- 顶部：项目名、保存状态、检测方式、摄像头状态。
- 左侧：动作列表，每项含名称、有效示例数量、可用状态；可新增动作。
- 中部：摄像头与骨骼叠加；下方录制进度与示例时间轴。
- 右侧：“动作说明”“执行效果”“匹配设置”。
- 底部：录制示例、训练动作、开始运行；用文字解释不可点击原因。
- 建议以 1440 × 900 桌面视口设计，在 1280 × 800 下可操作；小窗口允许合理滚动。
- 风格：黑白灰的中文工具界面，浅灰底、白色面板、深色文字，不使用绿色主题。录制与运行状态通过图标、边框和文字表达。

### D. 录制与训练

用户新建“动作 A”，选择效果，三秒倒计时后录制，默认录三秒，可设一至六秒或手动停止。建议录三至五次不同位置的正例，但这不是保证准确的样本数量。

每条示例保留时间戳、骨骼数据、有效帧信息、特征配置。提供基于骨骼的回放、删除与重新录制，默认不保存原始视频。提示收集“非目标动作”作为负例以调整误触发；无负例时明确校准有限。

训练后显示有效模板数、校准状态与存在问题；数据不足或丢失严重时说明原因，不显示虚假的训练动画或准确率。

### E. 实时运行

显示每个动作的匹配程度、检测质量、当前状态与最近触发。匹配程度是算法分数，不是“正确概率”；动作进度只有实现可靠的序列对齐后才显示。

运行状态包括“等待动作”“正在匹配”“动作完成”“等待复位”“暂停”“追踪丢失”。保留一个明显的停止按钮。用户切换配置或修改示例后，对应模板标为待训练。

## 5. 动作表示：位置无关不等于删掉全部运动

默认忽略画面绝对位置，对合理范围内的拍摄远近变化做尺度归一化。默认保留左右、上下方向；不自动认为旋转、镜像和倒序是同一动作。

- 手部形变：以手腕为参照，使用稳定掌部尺度归一化，提取相对关键点、关节角与指间距离。
- 整手轨迹：另外保留手腕相对片段起点的位移，按片段的稳健掌部尺度归一化，保留画圈等整体运动。
- 身体：髋中心作局部参照，躯干尺度归一化；根节点轨迹作为独立通道。
- 面部：表情优先选取相关 blendshape 系数或局部几何特征；头部朝向、头部位移为独立通道，不能被对齐处理全部消除。
- 提供“形变 / 运动轨迹 / 两者结合”的中文解释；预设用于降低用户负担。
- 先以 XY 验证；Z 为可选实验项。单目模型估计深度不能视为可靠的实测深度；各检测器的坐标定义不同，不直接混用。
- 显示镜像只影响预览；推理坐标、左右手标签与录制约定必须一致并记录在项目中。
- 每个检测适配器保留自身实际提供的质量指标，不编造每点置信度。尺度接近零或关键点不足时标为无效。

## 6. 时序匹配与触发设计

首版候选为带约束的 DTW 模板匹配。选择它是因为当前示范较少，目标是比较动作变化过程；这是待验证的设计，不保证任意动作都能可靠识别。

1. 以单调时间戳采集数据，按固定时间间隔重采样；避免直接按帧序号比较速度。初始特征采样目标 20 Hz，匹配检查 10 Hz，均可调整并记录。
2. 使用因果平滑；只允许很短的缺失插值，长时间丢失清空候选并暂停触发，不能用零填充伪造轨迹。
3. 录制模板包含完整动作起点、过程和终点；支持裁去准备与结束的多余部分。
4. 对流数据建立有限长度环形缓冲。候选可采用多个持续时长的后缀窗口，与完整模板比较；例如模板时长的 0.7～1.5 倍作为初始可调范围。
5. 轨迹坐标以每个候选窗口自己的起点重建，不能在无限流最初一帧固定原点。
6. DTW 使用受限时间扭曲和按路径长度归一化的距离；特征通道先尺度统一，再加权。限制路径斜率/步进，防止停留或局部动作被拉伸成完整动作。
7. 必须覆盖模板起点至终点，并检查最短时长、起终点门限、足够运动量与候选有效帧比例。只完成动作前半段或只停在最终姿势，不应触发。
8. 每个动作有自己的阈值。用留出正例与负例校准；数据不足则用可调初始阈值并明确状态，不把回测训练样本的结果当泛化准确率。
9. 多动作同时接近时要求最佳候选相对第二名有足够区分；模糊情况不触发。分数与距离的关系要在代码中明确，界面不称其为概率。
10. 触发状态机：等待 → 候选 → 完整匹配 → 触发一次 → 等待复位 → 等待。复位须匹配分数下降或检测到动作退出，同时满足冷却时间；不能只用定时器防重复。

上述数值是起始配置，不是已经测出的性能或识别保证。若 DTW 在真实案例上表现不足，再比较其他时序模型，避免首版先引入大规模自训练。

## 7. 软件结构与数据

核心逻辑不依赖 React、浏览器存储或 Electron：

```text
摄像头 → 检测适配器 → 带时间戳的观测 → 特征处理
      → 模板构建 / 实时匹配 → 触发状态机 → 效果执行器
```

界面负责交互；Worker 尽量承担同步视觉推理与时序计算。实现时验证 Worker、帧传输及 GPU/CPU 路径兼容性。限制在途帧，处理不过来就丢旧帧，不能堆积延迟。

接口保持轻量，至少分开 Detector、FeatureExtractor、SequenceMatcher、ActionExecutor。检测结果用区分类型表示 landmarks、object detections、semantic annotations，不将未来物体框或文字强塞进骨骼数组。

项目文件包含：schemaVersion、名称、检测模式、检测模型及特征版本、镜像约定、动作列表、示例序列、负例、模板参数、阈值、效果映射。时间戳保存为片段相对时间。相同示例与版本配置应产生可重复模板。

浏览器使用 IndexedDB 保存，支持 JSON 项目导入导出；导入检查版本、数组大小、数值有效性。桌面适配本地文件保存；通过受限 preload 桥接文件能力，不向渲染页面开放完整 Node.js。模型、WASM 和必要资源在桌面版随应用打包。

## 8. 未来视觉扩展

| 能力 | 职责 | 建议接入方式 |
| --- | --- | --- |
| 物体检测 | 物体类别、位置框，按需增加跨帧追踪 ID | 评估专用目标检测器，如 YOLO 系列；另测浏览器运行与模型许可 |
| GPT 视觉理解 | 解释画面或物体、产生语义描述与标签 | 显式启用的异步语义适配器，按需发送截图或裁剪图 |
| 颜色追踪 | 特定颜色区域的位置、面积、轨迹 | 可选轻量输入源；受光照影响，不是手脸身体识别的替代品 |

本地物体检测负责稳定框选，GPT 用于补充理解。不要承诺 GPT 精确、低延迟地逐帧返回稳定框；官方视觉文档提示空间定位存在局限。

云端功能不阻塞本地动作管线。标注请求中的状态、返回时间和来源，对旧画面结果做过期处理；请求失败不破坏本地匹配。标签与框保留来源与 frameId；自由文字不得直接触发系统命令。

用户明确开启后才发送图像，并说明发送范围；密钥不写入前端源码、项目导出文件或浏览器持久化项目数据。桌面使用系统安全存储与主进程调用；公开 Web 版另做服务端凭证方案。具体模型、API 接口与费用在该阶段选定。

## 9. 实施阶段与验收

### M1：验证核心动作能力

手部检测、真实三秒示例录制、骨骼回放、模板构建、实时动作匹配、应用内效果、保存与重新打开构成端到端闭环。不能只交付静态界面或随机匹配分数。

### M2：完整首版 demo

接入面部与身体两种单独可用的模式，完成中文解释、异常状态和三种检测模式的录制—匹配闭环。姿态分类、连续控制与云端理解仍不冒充可用功能。

### M3：Mac app

Electron 本地封装，摄像头权限、本地模型离线加载、项目文件读写与效果执行实测。先验证当前 Mac 架构，其他架构单独构建验证。个人可运行 .app 与正式签名、公证的分发版本分开交付和报告。

### 验收方法

- 使用真实目标动作，留出未参与模板构建的测试示例。
- 画面左、中、右位置测试；在约定取景范围内进行近远变化与速度变化测试，记录结果。
- 反向动作、只做一半、保持最终姿态、随机活动与追踪丢失作为负面测试。
- 单次完整动作只触发一次；复位后再次完成动作可重新触发。
- 面部、身体各提供至少一个真实动态示例，确认不是只有检测叠加层。
- 保存再打开，恢复示例、配置、阈值与效果映射；停止时释放摄像头与 Worker。
- 记录测试设备、浏览器/应用版本、检测频率、匹配耗时、动作完成后的触发延迟、误触发与漏检；不在测试前承诺准确率或固定帧率。
- 性能初始目标可设持续检测约 20 Hz、动作完成后额外延迟不超过约 300 ms，属于待测目标，失败应报告瓶颈，不伪造通过。
- 核心算法测试覆盖平移/尺度变换、保留方向、倒序/局部动作、缺帧与状态机复位；UI 验证中文可读、按钮状态和低分辨率窗口布局。
