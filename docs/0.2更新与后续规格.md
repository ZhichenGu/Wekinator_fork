## Serial 的配置与含义

选择输出方式为 Serial，点击“选择设备”，在浏览器的设备窗口中授权。之后页面可列出该网站已授权的串口；不会伪造系统设备路径。浏览器列表用序号与 USB 标识区分设备，首次设备名称以系统选择窗口为准。

选择波特率、连接，填入成功时发送的 UTF-8 文本，例如 `/success`、`1`、`0`、`YES`。结束符独立选择不追加、LF 或 CRLF。字符串 `0` 不会被当作空值；输入的反斜杠文字不会偷偷解释为转义序列。

一个完整动作触发一次发送。未匹配时不发消息，断线不排队补发。发送完成表示写入串口流，不等于设备已执行；目前未实现 Arduino 的应用层回执协议。真实硬件实测仍待进行。

## MQTT 应该填写哪些字段

当前页面已实现：

| 字段 | 示例/用途 |
| --- | --- |
| Broker WebSocket URL | `wss://主机:端口/mqtt`；端口和路径由 Broker 管理方提供 |
| Username | Broker 要求时填写 |
| Password | Broker 要求时填写，只保留在本次会话，不写入项目或导出文件 |
| Client ID | 可选；留空会为本次连接生成 ID |
| Topic | 例如 `my-project/action-a`，这是消息主题，不是 Broker 的项目创建入口 |
| 消息内容 | 例如 `YES`、`0`、`/success` |
| QoS | 0 或 1；1 可等待 Broker 的接收确认，仍不是设备执行确认 |

网页使用 WebSocket。无需再同时填 MQTT TCP 端口；若完整 URL 已含端口，也不另设重复端口框。MQTT TCP、TLS TCP 和 WebSocket 是不同连接方式，端口不能互换。不要假定所有 Broker 的 WebSocket 都使用某个统一端口或路径。

操作：填写 → 保存配置 → 连接 → 测试发送/开始运行。有未保存修改时禁止测试发送和启动 MQTT 自动输出。保存配置不会自动联网。HTTPS 页面需 WSS。重开项目不自动连接；需要认证时重新输入密码。

发布不使用 retain，断线不自动重连或补发。QoS 1 本身允许协议级重复，接收端控制硬件时如果需要严格去重，应在后续协议中加入事件 ID 和接收端去重。

不设置空的 Others 面板。有明确的新输出目标时再增加适配器。

## 单手、左右手与双手：建议与现状

当前仍是单人、单手模式，检测结果未把左右手约束作为训练条件；并未实现双手。

下一阶段建议提供“任意单手（默认）/仅左手/仅右手/双手”。普通单手动作不要求用户先选左右手；确实需要限制时放在高级设置。录制开始时自动保存 handedness 是有用的，但它不能替代整个运行过程的身份追踪：手会交叉、遮挡、进出画面，检测数组顺序也不能代表固定左右手。

双手模式应按左右手建立稳定数据槽，同时保留两手间距离和相对关系；缺一只手时标记无效，不补零伪造动作。不能只把两个模型输出数组无条件拼起来。它需要新的特征版本，旧单手模板不应直接混用。

## 另外两种学习方式：按顺序开展

当前动态动作匹配继续可用。下面两项仍显示规划中，尚未交付：

1. 姿态分类：先做。给不同姿态录入示例，用当前一帧或短时间稳定窗口判断类别，加“未知/不确定”状态；类别进入时触发一次状态灯、Serial 或 MQTT。静态姿态不能被当前“运动量不足”的动态模板规则拒绝。
2. 连续控制：随后做。录制输入与目标数值的配对数据，预测连续值。需要数值范围、平滑和输出频率限制，Serial/MQTT 消息格式应支持数值，而不是每帧发送固定 YES。

两者需要各自的数据、训练与验证流程，不应只是复用动态模式界面或替换名称。

## 对当前识别效果的检查

已修复：视频拉伸、旧加载会话干扰、重复模板浪费、缺少删除、配置精度及未保存 MQTT 输出等问题。

尚缺少的关键证据：独立真实动作测试集。当前匹配分数不是准确率，不能把训练样本上的成功回放称为识别达成率。本轮合成数据测试和空白帧模型测试也不能替代真实摄像头实测。

下一阶段建议建立独立“测试动作”流程：

- 正例包含不同位置、远近和速度，测试录制不参与模板构建；同一段录制的复制不能同时进入训练和测试。
- 加入只做半段、倒序、保持终点、随机动作、遮挡等负例。
- 分别报告完整动作成功数/测试次数、漏检、误触发次数/观察分钟数、完成到触发的延迟；不同动作分别统计。
- 用验证数据选择每个动作自己的阈值，再固定阈值进行留出测试；不要靠主观把所有阈值统一调低。
- 多个动作容易混淆时，增加区分性的正例与负例，或调整关注的形变/轨迹通道。真实录制的质量和覆盖范围，比复制数量更重要。

## 物体检测与 API Key

物体检测可以优先用本机模型输出框、类别与置信度，不必为了框选先接云端 API。类别范围由模型训练集决定；“拥有 API Key”不意味着可识别任意物体或可靠逐帧定位。

建议的新工作流：物体检测输入 → 绘制框 → hover 显示 label → 用户选择 label 并设置稳定出现时间/区域等触发条件 → 复用状态灯、Serial、MQTT 输出。hover 默认只解释对象，不自动触发硬件。对象持续存在时不得每帧重复发送，应采用进入/退出与复位机制。

该工作流尚未实现。云端理解确有必要时再加入提供商、接口、模型与凭证配置；密钥不能写入导出项目或前端发布包。当前不新增一个没有明确用途的 API Key 输入框。
